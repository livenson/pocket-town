# Decisions

One entry per decision: date, choice, reason. Newest at the bottom.

## 2026-11-07: rendering and UI stack

**Choice:** PixiJS v8 for the play stage, React 19 DOM for all menus and controls, plain TypeScript for the simulation.

**Why:**
- The game is heavy on interface (wizards, docks, sheets, cards, settings, a parental gate). Real DOM elements give screen-reader support, keyboard focus and voice-over hooks for free; canvas-drawn UI (Phaser, Godot) would need all of that rebuilt.
- PixiJS is a small, fast 2D renderer (about 0.2 MB empty build) with active releases (v8.19 in June 2026). It doesn't force a scene or physics model, which suits a 2D dollhouse with no physics.
- Keeping the sim free of rendering code makes it deterministic and unit-testable.

**Alternatives considered:**
- **Phaser 4** (stable since April 2026, rebuilt WebGL renderer): a full 2D framework with scenes, input, tweens and audio, and the largest community. A good choice for an action game; less so here because its UI is canvas-drawn.
- **Godot 4.x web export:** free and open source, but web builds are large (about 9 MB gzipped empty), C# can't export to the web, and Safari on iOS has known problems. iPad Safari is the main target.
- **Excalibur.js:** TypeScript-first with an ECS, but still pre-1.0 with a smaller ecosystem.
- **Defold:** smallest and fastest-loading builds, but Lua and a separate editor, and UI accessibility would again be custom.

**Revisit if:** characters need skeletal animation beyond what code-drawn pegs can do (consider Rive or Spine runtimes, both of which have web runtimes), or native app packaging becomes a goal (wrap the web build with Capacitor before considering an engine switch).

Sources: [Best web game engines for 2026 (cinevva)](https://app.cinevva.com/guides/web-game-engines-comparison), [Phaser v4.0.0 announcement](https://github.com/phaserjs/phaser/discussions/7274), [PixiJS June 2026 update](https://pixijs.com/blog/june-2026), [PixiJS React v8](https://pixijs.com/blog/pixi-react-v8-live), [Rive character animation](https://rive.app/use-cases/character-animation).

## 2026-11-07: no server, no network

**Choice:** a static site with all data on the device (IndexedDB). No accounts, analytics or third-party requests.

**Why:** children's data rules (GDPR Article 8; COPPA if the game later targets the US) apply as soon as data leaves the device. The social features are designed but deferred until there is a consent process and moderation plan.

## 2026-11-07: self-hosted fonts and procedural sound

**Choice:** fonts via @fontsource packages; sound effects generated with ZzFX; voice-over via the Web Speech API as a placeholder.

**Why:** no runtime calls to Google or CDNs, no audio licensing, tiny downloads. Recorded voice can replace the speech wrapper later.

## 2026-11-07: TypeScript 7 and oxlint instead of ESLint

**Choice:** TypeScript 7.0 (the native compiler) for type-checking, and oxlint with type-aware rules (`oxlint-tsgolint`, built on the same native compiler) instead of ESLint + typescript-eslint. Prettier stays for formatting.

**Why:** the owner asked for the latest stable versions. TypeScript 7 has no JavaScript compiler API, so typescript-eslint (which supports TypeScript up to 6.0) cannot run on it. oxlint covers the rules we need (TypeScript, React hooks, jsx-a11y, Vitest, floating promises) and is what the current Vite React template ships.

**Revisit if:** a rule we need exists only as an ESLint plugin; oxlint can also load ESLint-compatible JS plugins.

## 2026-11-07: Content Security Policy in the production build

**Choice:** the build adds a `<meta http-equiv="Content-Security-Policy">` that only allows our own origin (plus `data:`/`blob:` for images, media and workers). It is build-only because the dev server needs inline scripts and a websocket.

**Why:** it turns the "no network requests except our own static files" rule into something the browser enforces. If PixiJS later needs `unsafe-eval` for shaders, import `pixi.js/unsafe-eval` rather than loosening the policy.

## 2026-11-07: app icon glyph and font subsets

- **App icon** uses the `house` glyph (house with a heart, "My house") in white on a tomato rounded square. Icons are generated by `scripts/make-icons.ts` with `sharp` (dev dependency only) and committed.
- **Fonts:** all @fontsource subsets are built so any name renders, but only the Latin and Latin Extended `.woff2` files are precached for offline play; other subsets download from our own origin on demand.

## 2026-11-07: audio unlock

**Choice:** ZzFX creates its `AudioContext` on import; `installAudioUnlock()` resumes it (and plays a one-sample silent buffer) on the first pointer, touch or key event, which is what iOS Safari requires.

## 2026-11-07: M1 choices

- **Parental gate built in M1, not M5.** The grown-up area and the hidden component kit exist from M1, so the real gate (number in words, keypad, gentle clear on a wrong answer) protects them from the start. The hidden `#kit` URL opens only the kit, which changes nothing.
- **Screen state machine without a URL router.** `src/app/machine.ts` is a pure reducer (go, back, home, gatePassed), unit-tested. The grown-up area locks again as soon as you leave it, and "back" never re-enters the gate.
- **Hint halo under calm motion** keeps a still marigold ring and only stops the pulse, so the hint itself is never lost.
- **Text labels** show when the setting is on or the player picked age 9 or older on the age screen (age kept in memory until profiles arrive in M5).
- **Voice-over** speaks a control's label on long-press (touch, 450 ms) or hover (mouse, 600 ms). A long-press that spoke does not also press the button, so children can "ask" what a button does. The Web Speech wrapper prefers an on-device voice so text never goes to a network voice.
- **Lint:** `jsx-a11y/prefer-tag-over-role` is off (`role="group"` and `role="dialog"` on a `div` are valid ARIA, and native `<dialog>` would fight the sheet animation); `typescript/consistent-return` is off in favour of the compiler's `noImplicitReturns`, which understands exhaustive `switch` statements.
- **Dev dependencies added:** `fake-indexeddb` (unit-test the IndexedDB settings store in jsdom) and `@axe-core/playwright` (WCAG 2.1 AA checks on every screen in e2e). Neither ships to players.

## 2026-11-07: M2 stage choices

- **One Pixi Application, lazy-loaded.** `src/stage/stage.ts` creates the app once and moves its canvas into whichever screen hosts it. The stage code is a separate chunk, so Pixi is not in the first download (the splash, menus and gate load without it).
- **`pixi.js/unsafe-eval`** is imported so Pixi never needs `eval`/`new Function`; the production Content Security Policy stays strict (no `unsafe-eval`).
- **Room fitting.** Landscape: "contain", top-aligned, letterboxed in the ground colour at the sides; the floor runs on below the room behind the bottom docks (as in `Scene-Tablet.dc.html`). Portrait (phones and tablets): "contain" would make the room tiny, so it is scaled to fill about 55% of the height and the sides are cropped, as in `Scene-Phone.dc.html`. The follow-cam (M4) will pan within it.
- **Portrait tablets** put the time pill and camera above a full-width object drawer; the drawer shows as many tiles per page as fit (3–6).
- **Character textures.** Each character's drawing is cached as a texture per appearance and eye state (`cacheAsTexture`, resolution 3 so it stays crisp when the room is scaled up), and redrawn only when the eyes change.
- **Screenshot tests** compare the stage at three viewports against baselines made on Linux, the CI platform (`npm run e2e:screenshots`, which runs in the Playwright Docker image). On other platforms that one test is skipped. `?still` freezes the stage clock at zero for these pictures; `#scene` opens the play stage directly.

## 2026-11-07: M3 simulation choices

- **World as plain data.** `src/sim/types.ts` is JSON-friendly (no classes), so saving in M4 is a straight copy; all randomness comes from a seeded mulberry32 state stored in the world.
- **Town.** Starter house (kitchen and living room, plus a bedroom through a door), a neighbour's house, café, park, library and music hall (`src/content/rooms.ts`). Bots live in the two houses. Beds sleep two.
- **Scoring** follows SIM.md exactly; gains are divided by 100 so the 0.05 wander threshold applies. Sleep's gain is whatever energy is missing. At night sleep gets a small base pull (`nightSleepBase`) as well as the ×4 boost, so bots go to bed even when not tired, and sleepers never wake before 07:00.
- **"Paused" bot energy** stops autonomy and also holds needs still, so paused bots never end up starving.
- **Chatting** needs a free partner: a bot only invites a bot that is idle or wandering, which then turns to chat back. That keeps the "bots never interrupt each other" rule.
- **Tidy** only ever removes things a bot left out (a gift ball after play). Anything the child places or moves is marked as the child's and is never touched by bots.
- **Sounds** for state changes (chime on a new activity, jingle on a need met, doorbell, Pocketese blips while chatting) play only for the room on screen, at most one of each per frame.
- **Test hooks in the URL:** `?seed=N` for a reproducible town, `?hour=N` to start at a time of day, `?still` to freeze for screenshots, `#scene` to open the play stage.

## 2026-11-07: M4 core-loop choices

- **A DOM target layer over the canvas.** Every character, placed thing, door, the floor and three floor spots is a real `<button>` positioned over the stage each frame (`src/stage/targets.ts`). One mechanism serves taps, drop targets (`elementFromPoint`), keyboard focus, screen readers and e2e tests; the Pixi canvas itself takes no input.
- **Tap a character to open its card** (the plan says long-press). Long-press already means "say what this is" everywhere else, and a six-year-old is more likely to tap; the card is one tap away from the stage, the dock and the keyboard (Enter on a focused character).
- **Redo on phones too.** The phone mock shows only undo in the top bar; the hard rule "undo/redo everywhere" wins, and five 56 px buttons fit on a 390 px phone.
- **Undo** records, for each child command, how to put things back: the touched bot's control state (not its position, so nobody teleports) or the placed thing. Redo re-applies the command; placed things keep their id. 100 steps.
- **Saves**: schema 1 with a migration table, written to two slots in turn (`pocket-town:save:a`/`b`) with a generation number; loading takes the newest slot that parses and passes shape checks, so a broken write always leaves the previous good copy. Saved 1 s after every child change, every 30 s, and on `visibilitychange`/`pagehide`. `?seed` and `?still` start fresh and never save.
- **Putting a placed thing away** is press-and-hold (destructive), from the "carrying" pill.
- **Photos** are stored as bytes plus a type, not as `Blob`s, because WebKit can refuse Blobs in IndexedDB. The album keeps the newest 60 and never offers sharing.
- **Sounds before the first tap are skipped** (browsers block audio until a user gesture), so opening the app never logs autoplay warnings.

## 2026-11-07: M5 onboarding choices

- **Each player has their own town.** Saves are per profile (`pocket-town:save:<profileId>:a`/`b`). The very first profile inherits a town saved before profiles existed, so earlier testing is not lost. The player's own character moves into the starter house as one of the bots.
- **Profiles** (faces only, up to six) are stored on the device; which player is active is not remembered, so every launch asks "who is playing?" (a sibling cannot land in someone else's town by accident).
- **Order of questions:** first launch asks the age, then shows the single "new player" face (as in the prototype). Later "new player" taps ask the age first, then go straight to the dice. While choosing, word labels already follow the age picked.
- **Splash** builds the town and continues by itself once the play stage code and fonts are loaded and at least 2.6 s have passed; a tap skips the wait. The Pixi chunk loads during the splash, so play starts without a pause.
- **Hint chain:** phone starts at the "+" (the drawer is folded away); tablets and desktops start at the cake. Hints are spoken as they change, show words only for age 9+, and are marked done for that profile when the map is opened. Under calm motion the halos stay as still rings.
- **Measured:** the e2e run reaches the map in 9–10 taps (target: under 15) and feeds the first friend in about 8 s of scripted play (target: under 60 s for an adult acting like a child).
- **Landscape fit keeps the floor above the drawer.** On wide screens (16:9 laptops) "contain" put the characters' feet behind the object drawer; the room is now scaled so the floor line where characters stand (y ≈ 500) ends above the bottom docks, letterboxing the sides a little more.
- **Without a GPU (or in automated test browsers) the stage draws at most 30 frames a second.** CI runners render WebGL in software, and drawing at full rate starved input handling. CI also runs e2e with 2 workers, a 60 s test timeout and 2 retries.

## 2026-11-07: languages (English, Estonian, Latvian)

- **One dictionary per language** in `src/i18n/strings.<lang>.ts`. English is the reference; the `Strings` type (derived from English) makes TypeScript reject a translation with a missing or extra key, and a unit test checks no label is empty. Phrases with names are small functions, so word order can differ per language.
- **One live `strings` object.** Switching language deep-copies the new words into it, keeping nested objects' identity, so code holding `strings.card` stays current; the app re-renders on change. Content names (drawer things, traits, buildings) also come from the dictionary.
- **Choosing:** grown-ups pick the language in the grown-up area (behind the gate). The default, "same as this device", follows the browser language (et → Estonian, lv → Latvian, anything else → English). `<html lang>` follows the choice.
- **Parental gate numbers** are written in the chosen language (`src/i18n/numbers.ts`): "forty-seven", "nelikümmend seitse", "četrdesmit septiņi".
- **Voice-over** uses an on-device voice for the chosen language and stays quiet when the device has none (rather than reading Estonian or Latvian with an English voice). Many iPads have no Estonian or Latvian voice; recorded voice can replace the Web Speech wrapper later.
- **Latvian display font:** Baloo 2 lacks proper glyphs for ā ē ī ū (the macron lands beside the letter), so Latvian uses Nunito for display text too. Estonian letters render correctly in Baloo 2.
- **Gender-neutral Latvian:** activities are verbs ("ēd", "guļ"), traits and moods are nouns ("Drosme", "Prieks"), so no label assumes a character's gender.
- **Word labels wrap** onto two lines at the button's width instead of being cut off, since Estonian and Latvian words are often longer.
- **The translations were written by Claude and need a native speaker's review** before children use them.

## 2026-11-07: M6 wizards

- **Avatar wizard** edits the character being made (new player, or later an existing one): nine steps in any order with a step rail, a dice that surprises only the current step, its own undo/redo for the draft, a turntable preview (drag to spin), and a name typed only for age 9+ (letters, numbers, spaces; never leaves the device). New peg-folk options: body shape (tall, middle, short), mouth (smile, grin, calm), clothes pattern (plain, stripes, dots, collar), accessory (glasses, bow, hat) with an extra colour. Personality always keeps three traits: a new pick replaces the oldest.
- **Houses are world data.** `world.houses` holds what the child built (plot, shape, four room spaces, colours, a 12-cell furniture grid per room). A small registry turns them into buildings, so bots use the furniture, live there, sleep there and visit. Save schema 2 adds `houses` (migration from 1 tested).
- **Every house edit is one undoable step** on the main undo stack: the command carries the whole house, and undo restores the houses and every bot's home as they were.
- **Grid pieces are real furniture**, scaled to fit a cell, in two rows (by the wall, nearer us), turned with "turn"; a taken cell gives a red cross and a gentle sound.
- **Rooms in a house join in a row**: the first space with a room gets the front door; the rest connect left to right.
- **Housewarming** sends up to three neighbours on a visit (doorbell, then home again within two game hours).
- **"My house" in the hub always starts a new house**; built houses appear below it and on the map. The pencil in a built house edits that house.
- **Narrow screens** stack the wizards (steps along the top, picture, then options); the house picture sizes its own row so it can never cover the steps.
- **Pixi's accessibility system is removed**: on touch devices it added a hidden "enable accessibility" button; the DOM target layer already provides accessible controls.

## 2026-11-07: M7 hub, gallery, map and coming back

- **Hub** shows the player's home (their character's house) as a live cut-away: each room with whoever is in it and what they are doing; tap a room to go in. The face top-left switches player. Built houses sit below the four tiles.
- **My characters** pages through everyone in town. The dice adds a surprise character; "new" opens the avatar wizard for a new character; tapping a card opens change / copy / move house / hold-to-say-goodbye (not for your own character). All of it goes on the undo stack (the whole cast is remembered for these steps). The curated names leave out the starter cast's names so no two characters share one.
- **World map** is drawn in the DOM: roads, pond, trees, each building with its own roof and icon, portrait pins for who is where (pins move along the road while travelling), a visitor flag with the guest's face on houses with a guest, a time-of-day dial, and the time controls.
- **"While you were away"**: when a town is opened (or the app comes back from the background) more than 10 minutes after its last save, the town runs forward for the time away (one game hour per step, capped at two game days, 10 real minutes = 20 game hours) and a postcard shows 3–4 moments, preferring different characters and different kinds of thing (visiting, music, eating, sleeping, playing, chatting). It shows only once the player is in their town, closes itself after 8 s, and any tap skips it.
- **Hold buttons** no longer cancel when a press starts: with pointer capture the browser sends "leave" events immediately, so sliding off is now checked by position. **Sheets** no longer move focus when their parent re-renders (that also cancelled holds). Both bugs would have hit children on touch screens.

## 2026-11-07: Kid play-testing tool (dev server only)

- **What**: `npm run feedback` (or `feedback:lan` for a tablet) starts the dev server with a dashed tab on the right edge. A child taps it, points at something, picks a face, talks and/or writes. Claude Code, running the `kid-feedback` skill, reads it, changes the game, and the child hears a short reply and taps keep, put it back or change it more. Kept changes are committed (not pushed); "put it back" stashes the change, so nothing is lost.
- **Never shipped**: the client is `src/dev/feedback/`, imported only under `import.meta.env.DEV && MODE.startsWith('feedback')`, so a build drops it (checked: no trace in `dist/`). The server side is a Vite plugin in `scripts/feedback/`, active only in `serve` with a feedback mode.
- **Privacy**: voices, screenshots and town snapshots stay in `feedback/` on this computer (git-ignored). Voice to text runs locally with whisper.cpp when installed; no online speech service, because a child's voice must not leave the device.
- **Words**: the tool's spoken prompts are in en, et and lv, but in a dev-only dictionary (`src/dev/feedback/strings.ts`) rather than the game's, so they don't ship.
- **Dev dependencies**: `html-to-image`, to take a screenshot of the DOM (with the WebGL stage's current frame swapped in as an image), and `@vitejs/plugin-basic-ssl`, because tablets only allow the microphone over https. Both are dev-only and never bundled.
- **Safety in the loop**: one change at a time. `take` needs a clean working tree, so the change being proposed is the only thing in it. New feedback waits while a change is in flight.

## 2026-11-08: A character from a photo or the camera (owner's request)

- **What**: in the grown-up area (behind the parental gate), a grown-up picks a photo or turns on the camera; the face is measured on the device and a suggested look (face shape, eyes and eye colour, eye size and spacing, brows, nose, mouth width, ears, skin and hair colour) is put on the player's character or a new one, then opens the normal avatar wizard to adjust. The camera view shows the suggested character beside it, copying smiles, blinks and an open mouth (MediaPipe blendshapes). Boy or girl is never guessed from a face.
- **Why MediaPipe Face Landmarker** (new runtime dependency `@mediapipe/tasks-vision`, Apache 2.0): Google's on-device face model for the web, running in WebAssembly in every target browser including iPad Safari. Google's browser LLM (Gemini Nano in Chrome) was considered: desktop Chrome only, not iPad, and a general model rather than a face measurer.
- **Latest version (owner's call)**: 1.2.2. Its WebAssembly runtime (SIMD build; iPadOS 16.4+) and the model (version 1, the latest) are copied into `public/face/` by `npm run face-model` and committed (about 18 MB), served from our own site, loaded only when used, and kept out of the offline precache.
- **No data leaves the device**: MediaPipe 1.x has a usage logger that posts to a Google server with no setting to turn it off. It is blocked twice: the Content Security Policy (`connect-src 'self'`) and a guard that answers any request to another site locally. Checked in the build: after 80 s of camera use, no request to Google was attempted and no CSP violation was logged. The CSP gained `'wasm-unsafe-eval'`, which lets WebAssembly compile and does not allow JavaScript eval.
- **Pictures are never kept**: photos and camera frames live only in memory while being read; the camera stops when a look is kept, the screen is left or the camera is stopped, and the face finder is closed on leaving (MediaPipe's guidance, so memory does not grow).
- **Best practices followed** (Google's web guide): VIDEO mode with `detectForVideo` only on new frames, GPU delegate with a CPU fallback, one landmarker switched between IMAGE and VIDEO, `close()` when done. Readings are smoothed over frames (majority for choices, running averages for sizes and colours) so the suggestion settles instead of flickering.
