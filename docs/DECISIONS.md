# Decisions

One entry per decision: date, choice, reason. Newest at the bottom.

## 2026-11-07: rendering and UI stack

**Choice:** PixiJS v8 for the play stage, React 19 DOM for all menus and controls, plain TypeScript for the simulation.

**Why:**
- The game is heavy on interface (wizards, docks, sheets, cards, settings, a parental gate). Real DOM elements give screen-reader support, keyboard focus and voice-over hooks for free; canvas-drawn UI (Phaser, Godot) would need all of that rebuilt.
- PixiJS is a small, fast 2D renderer (about 0.2 MB empty build) with active releases (v8.19 in June 2026). It doesn't force a scene or physics model, which suits a 2D dollhouse with no physics.
- Keeping the sim free of rendering code makes it deterministic and unit-testable.

**Alternatives considered:**
- **Phaser 4** (stable since April 2026, rebuilt WebGL renderer): a full 2D framework with scenes, input, tweens and audio, and the largest community. A good choice for an action game; less so here because its UI is canvas-drawn.
- **Godot 4.x web export:** free and open source, but web builds are large (about 9 MB gzipped empty), C# can't export to the web, and Safari on iOS has known problems. iPad Safari is the main target.
- **Excalibur.js:** TypeScript-first with an ECS, but still pre-1.0 with a smaller ecosystem.
- **Defold:** smallest and fastest-loading builds, but Lua and a separate editor, and UI accessibility would again be custom.

**Revisit if:** characters need skeletal animation beyond what code-drawn pegs can do (consider Rive or Spine runtimes, both of which have web runtimes), or native app packaging becomes a goal (wrap the web build with Capacitor before considering an engine switch).

Sources: [Best web game engines for 2026 (cinevva)](https://app.cinevva.com/guides/web-game-engines-comparison), [Phaser v4.0.0 announcement](https://github.com/phaserjs/phaser/discussions/7274), [PixiJS June 2026 update](https://pixijs.com/blog/june-2026), [PixiJS React v8](https://pixijs.com/blog/pixi-react-v8-live), [Rive character animation](https://rive.app/use-cases/character-animation).

## 2026-11-07: no server, no network

**Choice:** a static site with all data on the device (IndexedDB). No accounts, analytics or third-party requests.

**Why:** children's data rules (GDPR Article 8; COPPA if the game later targets the US) apply as soon as data leaves the device. The social features are designed but deferred until there is a consent process and moderation plan.

## 2026-11-07: self-hosted fonts and procedural sound

**Choice:** fonts via @fontsource packages; sound effects generated with ZzFX; voice-over via the Web Speech API as a placeholder.

**Why:** no runtime calls to Google or CDNs, no audio licensing, tiny downloads. Recorded voice can replace the speech wrapper later.

## 2026-11-07: TypeScript 7 and oxlint instead of ESLint

**Choice:** TypeScript 7.0 (the native compiler) for type-checking, and oxlint with type-aware rules (`oxlint-tsgolint`, built on the same native compiler) instead of ESLint + typescript-eslint. Prettier stays for formatting.

**Why:** the owner asked for the latest stable versions. TypeScript 7 has no JavaScript compiler API, so typescript-eslint (which supports TypeScript up to 6.0) cannot run on it. oxlint covers the rules we need (TypeScript, React hooks, jsx-a11y, Vitest, floating promises) and is what the current Vite React template ships.

**Revisit if:** a rule we need exists only as an ESLint plugin; oxlint can also load ESLint-compatible JS plugins.

## 2026-11-07: Content Security Policy in the production build

**Choice:** the build adds a `<meta http-equiv="Content-Security-Policy">` that only allows our own origin (plus `data:`/`blob:` for images, media and workers). It is build-only because the dev server needs inline scripts and a websocket.

**Why:** it turns the "no network requests except our own static files" rule into something the browser enforces. If PixiJS later needs `unsafe-eval` for shaders, import `pixi.js/unsafe-eval` rather than loosening the policy.

## 2026-11-07: app icon glyph and font subsets

- **App icon** uses the `house` glyph (house with a heart, "My house") in white on a tomato rounded square. Icons are generated by `scripts/make-icons.ts` with `sharp` (dev dependency only) and committed.
- **Fonts:** all @fontsource subsets are built so any name renders, but only the Latin and Latin Extended `.woff2` files are precached for offline play; other subsets download from our own origin on demand.

## 2026-11-07: audio unlock

**Choice:** ZzFX creates its `AudioContext` on import; `installAudioUnlock()` resumes it (and plays a one-sample silent buffer) on the first pointer, touch or key event, which is what iOS Safari requires.

## 2026-11-07: M1 choices

- **Parental gate built in M1, not M5.** The grown-up area and the hidden component kit exist from M1, so the real gate (number in words, keypad, gentle clear on a wrong answer) protects them from the start. The hidden `#kit` URL opens only the kit, which changes nothing.
- **Screen state machine without a URL router.** `src/app/machine.ts` is a pure reducer (go, back, home, gatePassed), unit-tested. The grown-up area locks again as soon as you leave it, and "back" never re-enters the gate.
- **Hint halo under calm motion** keeps a still marigold ring and only stops the pulse, so the hint itself is never lost.
- **Text labels** show when the setting is on or the player picked age 9 or older on the age screen (age kept in memory until profiles arrive in M5).
- **Voice-over** speaks a control's label on long-press (touch, 450 ms) or hover (mouse, 600 ms). A long-press that spoke does not also press the button, so children can "ask" what a button does. The Web Speech wrapper prefers an on-device voice so text never goes to a network voice.
- **Lint:** `jsx-a11y/prefer-tag-over-role` is off (`role="group"` and `role="dialog"` on a `div` are valid ARIA, and native `<dialog>` would fight the sheet animation); `typescript/consistent-return` is off in favour of the compiler's `noImplicitReturns`, which understands exhaustive `switch` statements.
- **Dev dependencies added:** `fake-indexeddb` (unit-test the IndexedDB settings store in jsdom) and `@axe-core/playwright` (WCAG 2.1 AA checks on every screen in e2e). Neither ships to players.

## 2026-11-07: M2 stage choices

- **One Pixi Application, lazy-loaded.** `src/stage/stage.ts` creates the app once and moves its canvas into whichever screen hosts it. The stage code is a separate chunk, so Pixi is not in the first download (the splash, menus and gate load without it).
- **`pixi.js/unsafe-eval`** is imported so Pixi never needs `eval`/`new Function`; the production Content Security Policy stays strict (no `unsafe-eval`).
- **Room fitting.** Landscape: "contain", top-aligned, letterboxed in the ground colour at the sides; the floor runs on below the room behind the bottom docks (as in `Scene-Tablet.dc.html`). Portrait (phones and tablets): "contain" would make the room tiny, so it is scaled to fill about 55% of the height and the sides are cropped, as in `Scene-Phone.dc.html`. The follow-cam (M4) will pan within it.
- **Portrait tablets** put the time pill and camera above a full-width object drawer; the drawer shows as many tiles per page as fit (3–6).
- **Character textures.** Each character's drawing is cached as a texture per appearance and eye state (`cacheAsTexture`, resolution 3 so it stays crisp when the room is scaled up), and redrawn only when the eyes change.
- **Screenshot tests** compare the stage at three viewports against baselines made on Linux, the CI platform (`npm run e2e:screenshots`, which runs in the Playwright Docker image). On other platforms that one test is skipped. `?still` freezes the stage clock at zero for these pictures; `#scene` opens the play stage directly.
